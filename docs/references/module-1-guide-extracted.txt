1. Purpose and Scope
This document defines the screens, behavior, data, APIs, permissions, validation, security rules, test cases, and implementation sequence for Module 1: User Management & Trust. The proposal assigns Registration & Login and Admin Dashboard to Shakibur Rahman Akash; User Verification to Maruf Hasan All Haddy; and Portfolio Showcase to Shibashis Das. Because all four features are in Module 1, this guide documents their interfaces and integration points. Coordinate shared data models and API contracts with teammates.
1.1 Product context
MicroJobs is a student-focused marketplace where students can find small paid tasks and employers can post jobs. This module creates user accounts, controls access by role, supports trust checks, lets students present their work, and gives administrators tools to moderate the platform.
1.2 Goals
Allow students and employers to register and sign in securely.
Separate student, employer, and administrator permissions.
Support verification using email, phone, or university ID, with a Verified Student badge after successful student verification.
Allow students to maintain a portfolio of projects, certificates, images, links, and work samples.
Allow authorized administrators to manage users, jobs, reports, disputes, and platform statistics.
Keep personal and verification information visible only to authorized users.

 | Registration flow
User opens /register and chooses Student or Employer.
User fills required fields; frontend displays clear validation messages.
Frontend submits to a server route over HTTPS.
Server validates and normalizes all values again.
Server checks whether email (and phone if unique) already exists.
Server hashes the password using a suitable password-hashing library such as bcrypt or Argon2.
Server creates the account with safe defaults: active account, unverified status, createdAt and updatedAt.
Server creates a secure session/cookie or uses the agreed authentication provider.
UI confirms success and directs the user to the appropriate dashboard or verification step.
Login flow
User opens /login and enters email and password.
Server validates input and finds the account by normalized email.
Password is checked against the stored hash; responses should not reveal whether the email exists.
On success, create/refresh a secure session and redirect according to role.
On failure, show a generic message such as “Email or password is incorrect.”
Logout invalidates the session and clears the session cookie.

 | 3.2 User Verification (owner: Maruf Hasan All Haddy)
The proposal permits verification by email, phone, or university ID. A student receives the “Verified Student” badge only after the relevant check is approved. Email/phone verification proves control of a contact method; university ID review is a separate identity/student-status check.
Verification method
 | Suggested flow
 | Data/status to retain
 | Email
 | Send one-time, expiring verification link or code; user completes verification
 | emailVerifiedAt; token hash and expiry only while pending
 | Phone
 | Send OTP through an approved SMS provider; rate-limit attempts
 | phoneVerifiedAt; never retain OTP after use
 | University ID
 | Student submits required evidence through a private upload; authorized reviewer approves/rejects
 | studentVerificationStatus, reviewerId, reviewedAt, reason; restrict access to evidence
 | Verification states
State
 | Meaning
 | Badge
 | not_started
 | No verification request
 | Not shown
 | pending
 | Request submitted and awaiting check
 | Not shown
 | verified
 | Required check approved
 | Show Verified Student badge only for approved students
 | rejected
 | Review did not pass; show safe reason and retry path
 | Not shown
 | Define with the team whether the badge requires university-ID approval specifically or whether email/phone verification is sufficient. The proposal lists these methods but does not define the exact policy.
Verification safety requirements
Verification tokens/OTPs must expire, be single-use, and be stored safely (prefer token hashes).
Rate-limit resend and verification attempts; add cooldowns to reduce abuse.
Do not expose university ID documents or sensitive verification notes to other users.
Log reviewer actions without logging OTPs, passwords, or document contents.
Provide a clear pending/rejected status and a controlled resubmission process.

8. UI / UX Requirements
Use a consistent header, navigation, spacing, typography, buttons, input styles, and alert styles.
Support mobile, tablet, and desktop layouts.
Every form needs labels, required-field indicators, inline validation, disabled/loading state, success feedback, and a useful error message.
Never rely on placeholder text as the only field label.
Use accessible keyboard focus states and meaningful alt text for portfolio images.
Use confirmation dialogs for account suspension, deletion, and other high-impact admin actions.
Show empty states (for example, “You have not added any portfolio projects yet”) and retry controls for failed data loads.
Do not show a Verified Student badge merely because email is verified unless that matches the agreed verification policy.
9. Security, Privacy, and Reliability
Area
 | Required implementation behavior
 | Password handling
 | Hash with bcrypt/Argon2; never log or return passwords/hashes; use a secure reset flow.
 | Sessions/cookies
 | Use HTTPS in production; HttpOnly, Secure, and appropriate SameSite cookie settings; define expiry and logout behavior.
 | Authorization
 | Check session and role on the server for every protected endpoint; enforce ownership for profile/portfolio changes.
 | Input validation
 | Validate all request bodies, params, and query values on the server; reject unexpected fields.
 | CSRF / XSS / injection
 | Use framework protections appropriately, escape/render user content safely, avoid unsafe HTML, and apply CSRF protections when relevant to the chosen auth design.
 | Rate limiting
 | Protect login, password reset, verification sends, and OTP attempts.
 | Privacy
 | Keep passwords, tokens, phone numbers, and student ID evidence out of public APIs; minimize data collected.
 | Uploads
 | Limit size and file types; verify content; use safe filenames; prevent executable uploads; restrict private evidence access.
 | Admin safety
 | No public admin registration; audit important actions; protect admin sessions and account recovery.
 | Secrets
 | Keep database URI, auth secrets, email/SMS keys, and storage keys in environment variables; never commit .env files.
 | Database
 | Use least-privilege credentials, indexes, backups, and careful error handling.
 | Logging
 | Record useful events while redacting passwords, tokens, OTPs, and sensitive document data.
 | The proposal targets pages loading within 3 seconds under normal conditions and API responses within 1–2 seconds. Treat these as performance targets to measure, not guarantees.

 | 12. Acceptance Criteria
A student can register and log in; an employer can register and log in.
Registration cannot create an admin account.
Duplicate email registration is rejected safely.
Passwords are stored only as hashes.
Signed-out users cannot access private profile or admin APIs.
Students and employers cannot access admin routes or perform admin API actions.
Users can edit only their own permitted profile fields.
Verification state changes only after the corresponding verification process succeeds or an authorized review approves it.
Only approved students receive the Verified Student badge according to the team's policy.
Students can create, update, and delete their own portfolio items; employers can view public items only.
Admin can search users and moderate the agreed user/job/report/dispute resources.
Sensitive admin actions create audit records.
The interface is responsive and displays loading, empty, success, and error states.
No secrets or sensitive verification evidence appear in client responses or logs.
